# 五大關鍵約束：完整說明

SKILL.md 摘述了這五項；本文補充量化推理、程式實作模式與失效樣態。

共同特徵：**它們都產生「看起來正常但實際上錯誤」的資料**。
這比直接崩潰危險得多——崩潰會立刻被發現，錯誤資料可能到論文審查階段才暴露。

## 一、自動功能會讓校正失效

### 為什麼危險

相機校正取得的內參（焦距、主點、畸變係數）假設光學系統固定。
自動對焦改變焦距即改變內參；自動曝光改變亮度分布會影響姿態估計的一致性；
自動白平衡改變色彩會干擾以顏色為線索的人物區辨。

其中自動對焦最致命，因為：
- 它會在錄製**中途**觸發（人員走近走遠時）
- 影像看起來依然清晰正常
- 三維重建仍會產出數值，只是系統性偏移
- 除非用已知尺寸物件驗證，否則無從察覺

### 實作模式

```python
def _set_and_verify(cap, prop, value, prop_name, tol=0.51):
    """設定後必須回讀。部分 UVC 驅動靜默忽略設定請求，set() 仍回傳 True。"""
    cap.set(prop, value)
    actual = cap.get(prop)
    ok = abs(actual - value) <= tol
    if not ok:
        logger.warning("%s 設定未生效：要求 %s，實際 %s", prop_name, value, actual)
    return PropertyCheck(prop_name, value, actual, ok)
```

自動對焦的處理應與其他項目不同——**無法關閉時應中止而非警告**：

```python
autofocus = _set_and_verify(cap, cv2.CAP_PROP_AUTOFOCUS, 0, "autofocus", tol=0.01)
if not autofocus.ok:
    cap.release()
    raise RuntimeError(
        f"相機 {name} 無法關閉自動對焦（回讀值 {autofocus.actual}）。"
        "自動對焦會使相機校正失效，不得在此狀態下錄製。"
    )
```

### 平台陷阱

- **DirectShow 的自動曝光慣例與直覺相反**：`0.25` = 手動、`0.75` = 自動。
  此慣例因驅動而異，務必回讀。
- **曝光值採 log2 秒**：`-6` 約等於 1/64 秒。數值愈小曝光愈短。
- Windows 上應使用 `cv2.CAP_DSHOW` 後端；`CAP_MSMF` 在多相機同開時不穩定。

### 硬體層面的根本解法

選用**固定對焦（fixed focus）**機型，例如 Elgato Facecam 系列。
根本不存在自動對焦跑掉的可能，是最省心的選擇。

## 二、捲簾快門的系統性誤差

### 量化推理

感光元件逐行讀出，全幀讀出時間 `T_readout`（典型網路攝影機 720p60 約 8–15 ms）。
若目標物佔畫面高度比例 `h`，則其上下緣的取樣時差為 `h × T_readout`。

角速度 `ω` 下的視角傾斜誤差：

```
誤差 ≈ ω × h × T_readout

軀幹佔畫面一半（h = 0.5）、T_readout = 12 ms：
  一般速度 ω = 100°/s  →  100 × 0.5 × 0.012 = 0.6°
  快速施力 ω = 200°/s  →  200 × 0.5 × 0.012 = 1.2°
```

相較免標記系統本身 4–6° 的基線 RMSE，這增加約一至兩成。**不足以否定方案。**

### 為什麼仍需嚴肅處理

因為它是**系統性**的。若作業動作方向大致固定（翻身、單向搬運、產線重複動作），
誤差方向也固定，不會因樣本數增加而抵消，會表現為偏誤（bias）而非雜訊。

### 因應

1. **分速度區間報告效度。** 將試作依角速度分層，分別計算 ICC 與 RMSE。
   這能直接呈現誤差與速度的關係，讓讀者判斷結果在其應用情境下是否可信。
2. **以參照系統量化。** 用 IMU 或光學系統對照，實測誤差隨速度的增長。
   此分析本身即有方法學貢獻價值——目前少有文獻量化捲簾快門對職業作業量測的影響。
3. **加強照明縮短曝光。** 這減少的是動態模糊（影響姿態估計信心值），
   讀出造成的傾斜無法靠曝光解決。別誤以為打亮就沒事了。
4. **減少目標佔畫面比例。** 誤差與 `h` 成正比，相機退遠可降低誤差，
   但會損失空間解析度，需權衡。

## 三、多人場景

見 `multi-person.md` 的完整處理方案。此處只強調**為什麼這是架構層級的問題而非實作細節**：

若一開始以單人假設寫程式，資料結構會是 `frame → joints`。
改為多人後必須變成 `frame → {person_id: joints}`，且需要跨視角的 person_id 一致性——
這會波及三角測量、濾波、生物力學計算、資料庫 schema、視覺化的每一層。

**因此必須在 P2 設計資料結構時就預留多人維度**，即使 P2 階段只處理單人。

## 四、警示疲勞

### 自我否定的風險

若系統目的是降低工作負荷，卻因誤報頻繁而增加認知負擔，就構成邏輯上的自我否定。
既有文獻已證實警報負擔會顯著推升護理師主觀工作負荷
（Rasooly et al., 2021, *Hospital Pediatrics*）。

審查者或使用者一定會問這個問題。設計時就要有答案。

### 設計原則

**特異度優先於敏感度。** 這與多數醫療篩檢工具的取向相反，理由是：
漏報一次低風險姿勢的代價，遠低於誤報導致使用者關掉系統的代價。

**劑量準則而非瞬時閾值：**

```python
@dataclass
class RiskCriterion:
    metric: str              # 如 "trunk_flexion_deg"
    threshold: float         # 如 60.0
    min_duration_s: float    # 如 3.0 — 短暫彎腰是正常的
    cooldown_s: float        # 如 120.0 — 同類警示的抑制期
    require_load: bool       # 是否須併同負重判定
```

**被抑制的事件仍完整記錄。** 這是關鍵設計：

```python
# 不觸發警示，但寫入資料庫並記錄 suppressed_reason
RiskEvent(..., triggered_alert=False, suppressed_reason="cooldown")
```

如此才能事後分析「若閾值設為 X，誤報率與漏報率各為多少」，
把閾值調校從猜測變成資料驅動的決策。

### 驗收條件

把誤報率上限（如每 8 小時班 ≤ 2 次）寫進需求規格，
而非開發完再調參數。這會迫使設計階段就正視取捨。

### 延遲不是瓶頸

由於判定時間窗（3–5 秒）遠大於系統延遲（< 300 ms），
**不需要為降低延遲而過度優化架構**。真正的挑戰在警示決策邏輯。
這個認知可以省下大量不必要的工程努力。

## 五、雙管線

### 兩種需求的衝突

| 面向 | 離線研究管線 | 即時預警管線 |
|---|---|---|
| 首要目標 | 精度 | 延遲與可佈署性 |
| 相機數 | 全部（6 台） | 精簡（2–3 台） |
| 解析度 | 全解析度 | 降解析度 |
| 姿態模型 | 大模型 | 輕量模型 + TensorRT |
| 三角測量 | RANSAC + 時空正則化 | 簡化加權平均 |
| 逆動力學 | OpenSim | 連桿模型快速版 |
| 可接受耗時 | 數小時批次 | < 300 ms |

強行合一的後果：離線管線被即時需求綁架而降低精度，
即時管線被精度需求拖累而無法佈署。

### 切分方式

兩條管線**共用資料模型與生物力學核心**，僅擷取、推論與部署路徑分離。
生物力學指標的資料表應有 `computed_by` 欄位標記來源管線
（`fast_linkage` / `opensim`），避免兩者結果在分析時混淆。

### 意外的研究價值

即時管線的精度**不自行宣稱，而是以離線管線為內部黃金標準逐項量化**。
這讓「輕量化可佈署版本」具備明確的誤差界限，而非模糊的「大致可用」。

同樣邏輯可延伸為對照設計：量化「相機數由 6 減至 4、3、2 台時的精度衰減」。
這比「不同等級相機的比較」更貼近實際佈署決策——
現場真正會問的是「我最少要裝幾台」。
